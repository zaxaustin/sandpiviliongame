THE BUG THE DOC PASS FOUND
--------------------------

Reading MANUAL.md against the code to see what was stale, I went to check
what "the same schema, both homes" actually meant in db.cjs.

The Docker adapter never ran schema.sql. It never ran the migrations
either. Only openEmbedded() did.

The container got schema.sql exactly once, from the
docker-entrypoint-initdb.d mount in docker-compose.yml — which fires only
when the volume is empty and lists schema.sql alone, no migrations/. So
002 and 003 reached this machine's container BY HAND, months ago, and
nobody wrote that down. 004 — the next thing on the plan — would not have
reached it at all.

The design's whole claim is "one schema, two homes, nothing to drift."
That claim was true of one home. The waiting failure was the house one:
a named query referring to a table that exists in one home and not the
other, on a machine where every status line reads healthy.

applySchema() now runs the same files, in the same order, on both. The
two homes fail differently, on purpose:

  docker    NOT fatal. Throwing would drop through to the embedded
            database and split this machine's writes across two stores,
            which is worse than a schema that is behind. Keep the
            connection; report it. status() gained schemaError, kept
            SEPARATE from error, because a database that answers while
            being behind is the quiet fault most easily read as health.
  embedded  fatal. A schema-less fresh database is not a database, and
            there is no earlier store to split away from.

Broken on purpose, against the steward's REAL running container — the
first time the Docker path has been tested directly rather than by
pointing at a dead port:

  - new migration 999-proof.sql -> zz_proof appeared in the container.
    Could not have happened before this change. That is the positive
    proof, not an argument.
  - invalid SQL in it -> up:true, kind:docker, searchNotes still answers,
    schemaError: 'syntax error at or near "A"'.
  - same invalid SQL on the embedded path -> up:false, the error names
    BOTH homes, queries return null, the Pavilion carries on.
  - re-applying the real schema + both migrations to the live database:
    14 tables and views before, 14 after, notes_fts intact. Idempotency
    measured against real Postgres, not just PGlite.

The compose mount stays schema.sql-only. The entrypoint does not recurse
into a directory, so listing migrations there means a hand-maintained
list that has to match tools/migrations/ — rule 4's exact shape, and
every hand-maintained list in this project has drifted. Its comment now
points at db.cjs as the authority. Adding a migration is adding a file.

PHASE 2c — THE RECORDS HALL, AND THE BUG IT UNCOVERED
================================================================

"lets take our time and work on the things left undone"

THE ROOM

Was a hardcoded five-entry array frozen at 2026-07-10, while `records`,
`recordCounts` and `upsertRecord` sat in db.cjs with nothing calling them.
data/records.js now walks the save: books read, the Bench's builds,
investigations, experiments, packets given and received, and the Pavilion's
own milestones. Pure and deterministic - no model, no bridge, no clock it
was not handed.

ONE WALK, TWO READERS. The same gatherRecords() feeds both cases. With no
database the room is complete from the save and says outright that it is not
indexed; with one it is the same room, longer, merged on source_key so a row
the save no longer produces still shows. Not a second implementation of the
same idea - that is the store.js scar.

WHAT IT REFUSES. An undated build is skipped rather than dated today: a
record in the wrong year is a lie a note can cite. Notes, lessons and days
are deliberately absent and the file says why - notes already have their own
table and index, and "a lesson is finished" needs the lesson graph, which is
not reachable from the save. Guessing would put work in the visitor's history
that they never did.

14 OF 16 CARDS WERE DEAD ENDS

The first version named openInvestigation, openExperiment and openBuild as
the doors. None of the three exist. Found by opening the room and COUNTING
the clickable cards - not by reading the code, and not by any test that
existed. The standing rule is that nothing may be a dead end.

They point at openLab and openCommonsTable now, and npm test checks every
opener named in records.js against the window export block. That check earns
its place: openers live in the DATABASE as plain strings, so no amount of
static analysis of the calling code could ever catch a bad one.

THEN THE ACTUAL BUG, AND IT WAS NOT MINE

Nothing reached the database at all. Measured against the embedded home:

    []          failed        null      wrote
    ['a']       failed        '{}'      wrote
    ['a','b']   failed        '{a,b}'   wrote

A JS array passed for a TEXT[] parameter fails on PGlite. `tags` is the only
array column this app writes, and syncNotes passes null for it - so the
Records Hall's was the FIRST REAL ARRAY PARAMETER IN THE PROJECT'S HISTORY,
and it silently wrote nothing.

Fixed in normalizeParams(), below the named-query seam, so both homes get the
same Postgres array literal and the renderer still cannot tell them apart.
Arrays round-trip with contents intact now.

HONEST LIMIT: Docker Desktop was stopped, so the node-postgres half of that
table is documented behaviour rather than a measurement, and records.cjs
covers the embedded home only. Worth closing with the container up.

WHY IT TOOK A HAND-WRITTEN PROBE

writeMany returned null. So does "no bridge". And status() pings BEFORE
reporting, so the successful ping wiped lastError - the title screen read
"* Built-in database - your shelves, chapters and notes are indexed" the
entire time it was saving nothing. It was telling the truth about the only
thing it asked.

  - lastWriteError survives a later successful read
  - status() reports it as `writeError`, separate from `error`
  - data/backend-trouble.js owns the wording, DOM-free so npm test can hold
    it to account in a second without a browser - including the precedence:
    a write failure outranks a behind schema, because a behind-schema
    database usually cannot write either, and naming the schema would send
    someone to run migrations when the fault is elsewhere

THE PRINCIPLE, worth keeping: A FAILED READ IS SELF-REPORTING - the panel is
empty and you go looking. A FAILED WRITE IS NOT. It surfaces weeks later as
something missing that nobody watched being saved. The status line has to
work harder for writes than for reads, because reality does not report them.

That is ten times now that the measurement, the description, or the check
was the broken thing.
