THE DIAGNOSIS, which is the useful part
---------------------------------------
Everything in this Pavilion PRODUCES something. Almost nothing that
gets produced can become the INPUT to the next thing.

The chain the steward described already existed in pieces and broke at
exactly two joints:

  a book -> notes on it              WORKED (data.bookNotes, per page)
  notes -> a lesson plan             WORKED (since 2026-07-26)
  a plan -> a lesson in the tree     NOTHING. Not one line of code.
  a lesson -> something you're ON    NOTHING. No such concept existed.

Both breaks have the same shape: a thing was made and there was
nowhere for it to go. The AI writes a real, sequenced study plan and it
dies as text in a notes list. The tree holds lessons you can tick, but
nothing in the app knew which one you had picked up — so Today could
not offer it, the menu could not name it, and the tree could not put it
where you would find it again.

That is why it took "some finagling." Not a missing feature. A MISSING
JOIN. Same story in the Lab: reading produced notes, the Hall produced
dissections of PASTED papers, and neither knew the other existed, so a
book on your own shelf could not become an analysis you keep.

Written up as plans/THE-STUDY-CHAIN-PLAN.md before any code, because
the four asks needed to be shown to be one ask.

WHAT GOT BUILT
--------------
1. THE JOINT. data/plan-to-lesson.js parses a drafted plan into a
   walkable lesson — session/week/day/step headers, numbered lists,
   or bare paragraphs when the model ignored the shape entirely (it
   does). "🌳 Put this in the tree" sits on any note. Needs NO AI: a
   note you typed yourself converts identically. The note and the
   lesson stay linked both ways.

   Out in data/ so npm test can hold it to what a small local model
   ACTUALLY writes rather than what the prompt asked for — the lesson
   draft-parse.js cost a day in July.

2. PICKING ONE UP. data.study = {id, since}. One field, ONE path at a
   time, deliberately: you walk one or you walk none, and a list of
   active lessons is a second to-do list. What it buys: the tree opens
   on where you ARE, the pause menu names it, and THE DAY offers its
   next step FROM THE FIRST EVENING — the old inference needed a step
   already ticked, which is precisely the evening that decides whether
   there is a second one.

3. DISSECTING A BOOK. A dissection GAINS a book rather than a new
   store being invented: data.hall.dissections entries grow `book`,
   `question` and `passes[]`. The pasted-paper case is untouched
   because it works.

   The question is written FIRST, before any lens runs — same
   discipline as the Bench upstairs, and for the same reason: a
   dissection with no question is four AI paragraphs about a book,
   which is exactly the thing that used to evaporate.

   Four lenses (what is it claiming / what is it resting on / where is
   it weak / what do I do with it), each grounded in WHERE YOU
   ACTUALLY ARE — the page you opened it from, or the summary — and
   the panel says which, always. An appraisal of the blurb must never
   be able to pass itself off as a close read.

   "Pull in my notes" needs no model at all, and deliberately EXCLUDES
   notes the AI wrote: folding the model's own output back in as your
   evidence is how an analysis becomes a hall of mirrors.

4. THE READER'S BUTTONS. Thirteen identical ones in two
   undifferentiated rows, in the order they were added over four
   months. Now three labelled bands — LISTEN / WORK WITH THIS PAGE /
   MOVE. Nothing removed, nothing hidden behind a menu; a feature you
   cannot see is a feature you do not have.

SECOND PASS — the roles, and why the AI kept forgetting who it was
================================================================

The steward, after playing with the chain: "im worried about the local
ai memmory and that these differnt roles will confuse the ai instead of
it acting out its role when given a task."

Right, and the cause was not the number of roles. Two findings, both
measured rather than reasoned about.

1. THE CONTEXT WINDOW. Ollama runs every model at num_ctx 4096 unless
   told otherwise. `ollama ps` reported context_length 4096 for
   llama3.2, whose real window is 131k; ornith:9b's is 262k. The
   Pavilion sent num_predict on every request and never once sent
   num_ctx.

     prompt 7,279 tokens -> Ollama evaluated 2,050
     the model answered "I am Llama, a large language model by Meta AI"
     ...having been told in the first line it never saw that it was
     the Investigator.

   With num_ctx 16384: all 7,279 evaluated, role held perfectly. So the
   resident's identity was being deleted before the model saw it, every
   time a conversation or a grounded task got big. num_ctx is now sized
   per request, 4096 to 32k, powers of two.

   The other half of the worry was already sound: agent memory is keyed
   per resident, so Quill's has never been able to reach the Monk.

2. SEVEN PROMPTS EACH DESCRIBING THE OTHER SIX, BY HAND. They had
   already drifted: Sebastian's prompt told the model "Quill is the
   teacher", true in July and the Tutor's job by August. Same
   hand-maintained-list failure as hideAllOv and the window exports.
   Now data/roles.js is the one table and every prompt derives its
   roster from it; npm test fails on the stale phrases by name.

THIRD PASS — what the models actually know
================================================================

"whats the database of these local modles? is it just the library and
there offline? if so we should build a referance database for them for
basic science and math"

The honest answer: THEY HAVE NO DATABASE. A local model is a weights
file. Everything it knows was compressed in at training time and is
frozen; it cannot look anything up, and — the part that matters — it
cannot tell what it half-recalls from what it is confabulating. The
only database it gets is whatever the Pavilion pastes into the prompt,
fresh, every message. searchDocs() returns null: nothing anywhere can
look INSIDE a book. Quill is handed titles and blurbs and has never
read one.

Written up in plans/REFERENCE-AND-RETRIEVAL-PLAN.md, which separates
the two problems: it cannot look inside the books (retrieval), and it
cannot check a fact (the reference table). Built the second today.

THE CATALOGUE BUG, found while answering
----------------------------------------
Quill's prompt pasted the WHOLE catalogue — title, shelf, licence and
summary for every book — at ~43 tokens a book. Measured:

    27 shipped   ~1,150 tokens
   100 books     ~4,300
   500 books    ~21,400

So the librarian got slower and dumber the more books you owned, which
is exactly backwards for a Library "meant to be built from scratch by
its owner", and the steward had just imported a hundred. At 500 the
catalogue alone would fill the window.

data/catalogue-brief.js degrades in three stages: every book with
summaries while that is affordable, then titles only, then the SHAPE
(shelf names, counts, a sample). 130 books went from ~5,600 tokens to
1,650. The safety property is that a partial view SAYS it is partial —
otherwise the model confidently reports a book is not shelved when it
simply could not see it, which is a librarian inventing a No.

THE REFERENCE DESK
------------------
data/reference.js. Not "more for the model to read" — a small set of
values with a fixed right answer that it is NOT ALLOWED to make up.
Constants (SI-exact ones checked digit-for-digit in npm test), SI
prefixes, Ohm's law, dividers, RC, LED series resistors, resistor
colour code, E12, logic levels, the 38 kHz IR carrier, derivatives,
integrals, dB.

`ref <term>` at the Computer, and it needs no AI, which is the point.
The work residents get the matching entries injected — matched against
what the visitor actually asked, capped at six, told to prefer the
table over their own memory.

The guard caught a real bug on its first run: the symbol N_A normalises
to "n a", and a substring match hit "what did the monk MEA-N A-bout
right intention", so a question about right intention arrived carrying
Avogadro's constant. Matching is on word boundaries now. Funny once;
the same bug on a bigger table is the corpus-pasting habit wearing a
false-match costume — which is the exact failure the catalogue bug had
demonstrated an hour earlier.

THIRD SESSION - Round 5's list, and the first real-model probe
================================================================

Took the list in order: chapters, per-book notes, prompt weight. The
fourth thing was not on the list and is the one worth remembering.

CHAPTERS (#41) - and the diagnosis in the file was too generous.

  The cause was recorded correctly: chapterPages() read the first THREE
  LINES of each page, and a page is a 1,400-character slice. The effect
  was not. It was not "the first four chapters and then nothing."

      The Dhammapada   26 chapters   found 0
      The Bhagavad Gita 18 chapters  found 0

  Both ship in the welcome packet. Neither had ever shown a chapter
  control to anybody.

  THE WRITTEN CURE WAS WRONG, AND MEASURING IT IS WHAT SHOWED THAT.
  The plan said: parse the Contents block, then find each chapter name's
  SECOND occurrence in the body. Tried it. It lands on the wrong page
  constantly, because chapter titles are ordinary words - "Thought",
  "Self", "Happiness", "The World" all match prose on page 1 long before
  they match their own heading. Matching the whole Contents line does
  worse (14 of 26): the Contents says "Chapter 1: The Twin Verses" and
  the body says "Chapter I. The Twin-Verses". Arabic against roman,
  colon against period, and a hyphen.

  So the two sources swapped jobs, and that is the whole design:

      the BODY is the authority on PAGES   (anchored whole-line scan,
        whole page, every match - 18/18 in the Gita, 26/26 here)
      the CONTENTS is the authority on NAMES (the Gita's body headings
        are bare "CHAPTER IV"; the title exists only in its Contents)

  Three smaller rules, each from a real failure while building it:

    - a heading must carry a NUMBER, or "Part of the reason we do this"
      is a chapter break;
    - only the DOMINANT KEYWORD survives, which drops the Dhammapada's
      front-matter "Part I" with no special case for that book;
    - a Contents block COUNTS UP. Without that the block swallowed the
      body's real "Chapter I" - which looks identical to a Contents
      entry - and reported 27 chapters for a 26-chapter book.

  Falls back honestly: the four suttas have no chapters and now say so,
  rather than silently losing two buttons.

  Payoff, same day: a note records "ch. 5 - page 8", and the reader row
  reads "ch. 5 of 26" as you move.

PER-BOOK NOTES (#42). "Everything I wrote about THIS book", from the
  reader or the Books filter. Narrowed to one book it orders by the
  BOOK's order and groups under real chapter headings. Two things found
  only by looking at the rendered result: the card printed the book's
  name three times and the note's text twice; and a book note's page was
  rendered 0-based ("p.7" for the reader's page 8) and hidden entirely
  on page 1, a truthiness test on a zero.

PROMPT WEIGHT (#43) - trimmed, and the real weight was somewhere else.

  The prose was worth doing: the Investigator said the same thing three
  times, and came down 1,409 -> 1,187 always-on tokens with no rule
  dropped. The Monk was deliberately LEFT ALONE - his bulk is identity
  and the canon he can draw on, which is the enabling kind of prompt
  this project wants. The Investigator's bulk was restatement.

  But the prose was not the problem. Two blocks in the same prompt

    - every seeded investigation with its full verdict AND its grounding

    - every Science and Hindu text with its FULL SUMMARY, unbounded.

#45 - THE ONE THAT MATTERS: THE PRE-NOTES WERE LYING.

  First time any resident prompt has met a real model (ornith:9b)
  instead of being exercised on its no-AI path. Asked for pre-notes on
  two seed books:

    The Dhammapada -> "grouped into five thematic chapters: the Mind,
      Heedfulness, Anger, the Self, and the Path."

      It has TWENTY-SIX. The blurb listed five themes as examples and
      the model turned them into a structure. The visitor then opens the
      book and finds Chapter XXVI.

    The Tao Te Ching, from a 431-character blurb -> invented an author
      (Laozi), a technical term (wu wei), and a QUOTATION: "The soft

  The prompt already said "never invent a chapter title or a quotation"
  and "where the material given is too thin to say something useful, say
  that plainly instead of padding." It broke all three rules in one
  reply and never once said the material was thin.

  THE LESSON, and it generalises well past this prompt:

      A RULE THE MODEL HAS TO NOTICE IT IS BREAKING IS WEAKER THAN A
      FACT IT IS SIMPLY GIVEN.

  So: answer the question instead of inviting a guess. "HOW IT IS BUILT"
  has a real answer we now hold, because of the chapter work above.
  bookStructureBlock() hands over the actual page count and the actual
  chapter list. And state the thinness in NUMBERS, deterministically,
  rather than asking the model to judge it.

  Re-probed, same model:

    Dhammapada -> "The book runs 51 pages across 26 chapters, each named
      in its own table of contents (e.g., On Earnestness, Thought,
      Anger, The Way)." Correct, and it names the real closing chapters.

    Tao Te Ching -> "The text itself is not here; this preparation is
      drawn from the blurb alone, so no chapter structure or author
      attribution can be confirmed."

  Which is what it was asked for all along.

THE BACKEND. He asked whether to put a local SQL database under this. I
argued against it, from a wrong premise - I assumed leaving Supabase was
a local-first preference, so "51 rows don't need a database" followed.
His actual reason:

    "the reason we got off supabase was because it did not allow ai
     intergration on the backend"

That is a CAPABILITY argument, not a storage one, and it points the
other way. Postgres in Docker beside MinIO. MinIO keeps the text;
Postgres keeps what the Pavilion KNOWS - cards, shelves, 6,361
chapters, notes, records.

Two obstacles, both named rather than pretended away:
  - Store.allDocs() is SYNCHRONOUS and called mid-render. A query is
    not. So the catalogue hydrates ONCE at boot into the same in-memory
    list the seed fills, and no call site changes.
  - A browser cannot speak Postgres's binary protocol. Ever. The
    Electron main process can, and does. The web build keeps running on
    seed + localStorage, so nothing regresses, and it is still the only
    Mac answer.

WHAT THE DESK WAS. A day planner - intention, ember, rhythm blocks,
sparks - with ONE AI panel hardcoded to the Steward, carrying its own
system prompt, its own history and its own error line. It was the only
room in the Pavilion talking to a resident through plumbing nobody else
used. Meanwhile your notes, the book you were reading, and a lesson
being drafted each lived in a different room. A form you fill in, when
what he described is a desk you sit down at.

1 - CALL SOMEONE OVER. A picker of all seven residents, DERIVED from
data/roles.js (deskResidents()), never hand-listed - hand-maintained
copies of that org chart have drifted three times here. Each resident
answers through the same CHAT_AGENTS[key].systemPrompt() they use in
their own room, plus deskFraming() (what you called them over FOR,
taken from their own sendMe line) and deskStateBlock() (what is
actually on the desk).

ONE AT A TIME IS THE DESIGN. Each keeps a separate thread in
state.plannerChat.byAgent - calling the Tutor over must never hand her
the librarian's last four exchanges as if they were her own. That is
the difference between a personality and an agent: an agent is chosen
for a purpose.

The DEFAULT is the hub, derived rather than named. roles.js says the
day belongs to Sebastian, and the day is what this desk is. The old
hardcoded Steward predated that file.

2 - YOUR OLDER NOTES. The desk showed only today. It now shows what you
wrote LATELY and what is WORTH ANOTHER LOOK, and the resurfacing rule
is not a second copy: forgottenNotes() was lifted out of theDayItems()
into data/the-day.js and both call it. Deliberately a reader, not a
second editor - one place a note is written, one place they are
gathered. The filing cabinet is still underneath it.

3 - THE BOOK IN FRONT OF YOU. state.readerPocket already existed and
was used nowhere near here. The desk now shows the book you walked over
with - title, author, chapter, page - reopens it in one press, and
takes a note on it through writeBookNote(), the SAME path the Reader
uses, extracted so there is no second implementation. The note carries
the same chapter and page, and the same doors. An empty desk is not a
dead end: it carries the doors to a book.

4 - A LESSON DRAFTED IN NOTES, BEFORE THE WALL. deskDraftLesson()
grounds the local model in the book, the page actually in front of you,
and your own notes on it, and writes a lesson plan INTO A NOTE. Then it
stops. The model drafts, the person promotes - the same "a suggestion
is not a decision" line the shelf sorter's review step exists to keep.
Read it, edit it, then press.

--- THE CLOUD QUESTION, TESTED RATHER THAN GUESSED ---

He asked how the cloud connection with Ollama is, because a laptop
cannot host a local model and most of his friends are on laptops.

IT WORKS AND IT IS THE RIGHT ANSWER FOR THEM. Ollama serves hosted
models through the SAME local endpoint, so no API key is ever pasted
into this app: gpt-oss:20b-cloud answered in 0.64 seconds where a local
9B takes many. Install Ollama, sign in, pull a -cloud model, done. The
paid tier is real - deepseek-v4-pro:cloud returns "requires a
subscription".

AND TESTING IT EXPOSED THE HIGHEST-STAKES SILENT BUG IN THE PROJECT.
bestLocalModel() returned gpt-oss:20b-cloud on this machine. So the
Monk's standing rule - always the largest LOCAL model - would have sent
his most private conversations to a server, while the title screen said
"Running on this device alone."

The guard existed and had gone stale: it tested for a name ending in
":cloud", which was true of the naming a month ago and false of the
hyphen form the free tier actually uses. It was also in the wrong PLACE
- a display filter in one panel, a second copy of the same regex in
another, while chatOptsFor() read the raw unfiltered list. One
definition now, in provider.js where the list is built, on two
independent signals: the NAME, and the SIZE (a hosted entry is a
306-byte manifest where a real model is gigabytes). bestLocalModel()
returns null rather than falling back to a server when nothing local is
installed. Guarded with the ACTUAL output of ollama list on this
machine; restoring the old rule fails 4 checks, each naming what it
would have cost.

--- THE TEACHER'S TREE, gaps 1-3 of THE-TEACHERS-TREE-PLAN.md ---

1. A LESSON CAN CITE A BOOK. It was the one artifact in the Pavilion
   that could not, while a note has carried chapter and page since this
   morning. A set-text picker on the lesson, and per-step readings
   DETECTED from what was typed naturally - "Read chapters 3-4 and
   annotate", "Discuss pp. 12-18" - rather than a syntax a teacher has
   to learn. Where it finds nothing it says nothing: a lesson that
   cites the wrong pages is a class that goes wrong on Monday.

2. IT LEAVES AS A DOCUMENT. A packet is right for another Pavilion and
   useless in a classroom. Markdown, and ONE self-contained HTML file -
   styles inside it, nothing fetched, real print rules - that he can
   put on his own site. We render the file; the website stays his. Also
   fixed the save dialog, which hardcoded a JSON filter for every file
   including plain text.

3. A PUBLISHED LESSON COMES BACK AS A LESSON. It used to fall through
   takePacket()'s else branch into Your Notes as prose, so the
   collective tree could never grow - hand a colleague a lesson and he
   retyped it. Prerequisites travel as titles and are matched locally;
   unmatched ones are dropped rather than arriving locked.
