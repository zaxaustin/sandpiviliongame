1. THE DEBT: arrays on the Docker home
----------------------------------------------------------------

On 2026-08-04 a real, pre-existing bug was found and fixed: a JS array
passed for a TEXT[] parameter FAILS on PGlite. `tags` is the only array
column the app writes and syncNotes has always passed null for it, so
the Records Hall's was the first real array parameter in this project's
history, and it silently wrote nothing at all.

The fix normalises to a Postgres array literal below the named-query
seam, so both homes get the same form. But Docker Desktop was stopped
that day, so half the claim — "the two homes differ" — came from
node-postgres's documentation rather than from a run. That was written
down as an HONEST LIMIT in db.cjs rather than glossed.

Measured today, container up. All six forms, raw through node-postgres:

                embedded (08-04)   docker (08-07)
  []            failed             wrote
  ['a']         failed             wrote
  ['a','b']     failed             wrote
  null          wrote              wrote
  '{}'          wrote              wrote
  '{a,b}'       wrote              wrote

So the disagreement was real, and it was exactly the shape this design
exists to prevent: the renderer asks for a named write and must not care
which home answers. Confirmed too that the literal the fix now sends
works on Docker, that a tag with a space and a tag containing a `"` both
survive the round trip, and that [] arrives as an empty TEXT[] rather
than NULL.

Also confirmed, and this is the bigger one: applySchema() genuinely
reached the container. All 14 relations present — notes, records, the
four v_* views — and notes_fts intact. That was previously verified by
creating a test migration; today it was verified by looking at what is
actually in the running database, which is a different question.

2. THE PROBE BECAME A SUITE, AND CAUGHT ME
----------------------------------------------------------------

The throwaway probe was promoted to test/live/docker-home.cjs rather
than deleted, because the coverage gap it filled is permanent: the two
existing database suites (note-search.cjs, records.cjs) both redirect
userData and point POSTGRES_PORT at nothing on purpose, so they are
ALWAYS the fresh-embedded case. Nothing covered the container.

Before promoting it I wrote into db.cjs's comment that "the Docker half
is covered by test/live/backend.mjs." That was false. backend.mjs stubs
the desktop bridge so it can run in a plain browser — it has never
touched Docker. Caught by opening the file instead of trusting the
memory of it. The comment now points at the suite that actually exists.

The suite then caught bad test data of mine: notes.source carries a
CHECK constraint (mynotes|book|chat|research|grant|hall) and I passed
'probe'. Which is the point — db.write() returned its usual null, and
the only reason the failure was visible at all is status().writeError,
added three days ago precisely because a failed write does not announce
itself.

Broken on purpose (rule 3): POSTGRES_PORT=5999 makes it SKIP, print why,
and exit 0 — without falling through to the embedded home and reporting
on a database nobody asked about. It also had to be taught to read
process.env before .env, or it would have connected somewhere db.cjs was
not and agreed with itself.

  15 passed, 0 failed.

7. THE THREE COURTS, SETTLED
----------------------------------------------------------------

Asked where PAVILION-TIERS-AND-COMMONS-SERVER-PLAN.md was, the steward
answered that it isn't a file — the courts are new thinking:

  Outer = everyone, the whole public. ALL OF IT IS HERE TODAY.
  Inner = contributors.
  Core  = those on the path; a layman's sangha.

The earlier worry — that Outer/Inner/Core was a second vocabulary
competing with private/shared/commons — was WRONG, and saying so matters
because the two now have to coexist on the same screens.

  private/shared/commons is about a THING: where it is, whether it left.
  Outer/Inner/Core is about a PERSON: which circle they stand in.

A commons packet is commons whichever court you are in. They cross, they
don't compete. Recorded in NEW-PLANS-RECONCILED with two consequences:
everything today being Outer is the correct default rather than a gap
(the beta ships to strangers; nothing may require a court to work), and
the Core is NOT a higher rank than the Inner — the Mission ranks measure
work, the courts describe company, and rendering them as one ladder
would turn a practice into a score.

The Core's entry condition is deliberately left unspecified. It is the
steward's to say and the one place a guess would be disrespectful of
what the room is for.


8. PHASE 2d WAS THE WRONG SHAPE
----------------------------------------------------------------

"6 of 15 named queries have no consumer" had been carried as a debt.
Checked one at a time against rule 7 (deterministic code first), it is
not a debt — it is a design question, and four of the six should stay
unwired:

  searchNotes    stemming and ranking. JS cannot. WIRED, RIGHT.
  records        holds `hidden`, the visitor's own choice. WIRED, RIGHT.
  notesForBook   nothing gatherNotes() doesn't already do exactly and
                 instantly, in the renderer, on the web build too.
  notesByPlace   grouping and counting — rule 7 names counting as the
  noteCounts     thing code does exactly.
  unshelved      `books` mirrors personalLibrary, already in the save.
  shelfCounts

Wiring the middle four would be a second path over data the save already
holds. That is the store.js scar arriving through a new door.

THE CHAPTER QUERIES ARE NOT UNWIRED, THEY ARE BLOCKED. Nothing anywhere
writes `chapters` or `chapter_scans` — the only writer is
tools/load-library.mjs, the MinIO loader, Docker + manual + this machine
only. In the app findChapters() runs on open and the answer is discarded
on close. Worse, v_needs_chapters gates on `text_key IS NOT NULL`, also
loader-only, so on every machine that is not the steward's the view
returns ZERO ROWS ALWAYS.

Wiring it today would render "0 books need chapters" while 18 of 39
actually do. A specific, confident, wrong answer — rule 6's exact
prohibition, and worse than the current silence, because a panel saying
zero gets believed.

Doing it properly is three pieces (syncChapters + a new detected-chapter
WRITE, a migration to un-MinIO the view, then the panel), and piece 1
only learns about books already opened — so it must say so or offer a
deliberate sweep. Written up in NEW-PLANS-RECONCILED rather than half
built.


9. WHAT THE AUDIT WAS ACTUALLY POINTING AT — AND IT WAS A REAL BUG
----------------------------------------------------------------

notesForBook existed because the Reader can't see notes about a book
that were written elsewhere. That gap is real. The fix is JS, not SQL —
and hunting it turned up something worse in the Notes Log itself.

The book row exists to answer ONE question: "everything I wrote about
THIS book." It was answering it short, two ways:

  1. gatherNotes() gave `slug` only to source:'book' notes. The filter
     reads `n.slug !== v.book`. So a My Note LINKED to a book —
     note.book = {slug, page, chapter}, which is EXACTLY the shape the
     reader writes when it saves an AI analysis to My Notes — was
     dropped.
  2. openNotesForBook() pinned source:'book' as well as the slug. That
     is a second filter nobody asked for: "about this book" quietly
     meant "written INSIDE this book."

Nothing looked wrong because the chip's COUNT was short by the same
amount as the list. The measurement and the thing measured were wrong
together — the eleventh instance of that pattern in this project.

Fixed: bookSlugOf() normalises the three shapes a book link has ever had
(object, bare string, null) at the one place that already exists to put
notes in one shape; the chip counts any note naming a book; and
openNotesForBook leaves source at 'all', because where a note was
written and which book it is about are different axes.

Mid-fix I wrote `titleOfBook(n.slug)` — a function that does not exist.
Caught by grepping for it before building, which is exactly the
free-identifier crash the guard was written for, authored by the person
who wrote the guard.


10. LOOK AT IT — TWICE, AND THE SECOND TIME MATTERED
----------------------------------------------------------------

test/live/notes-by-book.mjs, 7 checks. Two things the assertions could
not have told me:

  * FIRST RUN: all text assertions passed while the screenshot showed
    the TITLE SCREEN covering the whole panel. innerText does not care
    what is on top of it. The test now clicks Enter the Grounds, and the
    visibility check uses elementFromPoint instead of `style.display`,
    which a covered panel satisfies happily.

  * The chip assertion initially read "1" and I nearly filed it as a
    second bug. The regex /📖[^\n·]*·\s*(\d+)/ was matching the SOURCE
    chip ("📖 Book · 1") before the book chip. A test that reads the
    wrong element and then agrees with the bug is worse than no test.
    It now finds the button by its onclick.

  * STILL OPEN, seen in the .png and not fixed: the two My Notes group
    under "No page — from the summary" though both carry a page. The
    grouping reads n.page, which My Notes carry inside n.book instead.
    NOT fixed on purpose: gatherNotes' own comment records that a My
    Note's page is 1-BASED and a book note's is 0-BASED, so hoisting it
    without the conversion would put a wrong page number on a note, and
    a note gets cited. Rule 6 — recorded rather than guessed.

Green: npm test, preflight (zero network), study-chain 39/39,
