1. THE DEBT: arrays on the Docker home
----------------------------------------------------------------

On 2026-08-04 a real, pre-existing bug was found and fixed: a JS array
passed for a TEXT[] parameter FAILS on PGlite. `tags` is the only array
column the app writes and syncNotes has always passed null for it, so
the Records Hall's was the first real array parameter in this project's
history, and it silently wrote nothing at all.

The fix normalises to a Postgres array literal below the named-query
seam, so both homes get the same form. But Docker Desktop was stopped
that day, so half the claim — "the two homes differ" — came from
node-postgres's documentation rather than from a run. That was written
down as an HONEST LIMIT in db.cjs rather than glossed.

Measured today, container up. All six forms, raw through node-postgres:

                embedded (08-04)   docker (08-07)
  []            failed             wrote
  ['a']         failed             wrote
  ['a','b']     failed             wrote
  null          wrote              wrote
  '{}'          wrote              wrote
  '{a,b}'       wrote              wrote

So the disagreement was real, and it was exactly the shape this design
exists to prevent: the renderer asks for a named write and must not care
which home answers. Confirmed too that the literal the fix now sends
works on Docker, that a tag with a space and a tag containing a `"` both
survive the round trip, and that [] arrives as an empty TEXT[] rather
than NULL.

Also confirmed, and this is the bigger one: applySchema() genuinely
reached the container. All 14 relations present — notes, records, the
four v_* views — and notes_fts intact. That was previously verified by
creating a test migration; today it was verified by looking at what is
actually in the running database, which is a different question.

----------------------------------------------------------------

"6 of 15 named queries have no consumer" had been carried as a debt.

not a debt — it is a design question, and four of the six should stay
unwired:

THE CHAPTER QUERIES ARE NOT UNWIRED, THEY ARE BLOCKED. Nothing anywhere
writes `chapters` or `chapter_scans` — the only writer is

Doing it properly is three pieces (syncChapters + a new detected-chapter

9. WHAT THE AUDIT WAS ACTUALLY POINTING AT — AND IT WAS A REAL BUG
----------------------------------------------------------------

notesForBook existed because the Reader can't see notes about a book
that were written elsewhere. That gap is real. The fix is JS, not SQL —
and hunting it turned up something worse in the Notes Log itself.

The book row exists to answer ONE question: "everything I wrote about
THIS book." It was answering it short, two ways:

  1. gatherNotes() gave `slug` only to source:'book' notes. The filter
     reads `n.slug !== v.book`. So a My Note LINKED to a book —
     note.book = {slug, page, chapter}, which is EXACTLY the shape the
     reader writes when it saves an AI analysis to My Notes — was
     dropped.
  2. openNotesForBook() pinned source:'book' as well as the slug. That
     is a second filter nobody asked for: "about this book" quietly
     meant "written INSIDE this book."

Nothing looked wrong because the chip's COUNT was short by the same
amount as the list. The measurement and the thing measured were wrong
together — the eleventh instance of that pattern in this project.

Fixed: bookSlugOf() normalises the three shapes a book link has ever had
(object, bare string, null) at the one place that already exists to put
notes in one shape; the chip counts any note naming a book; and
openNotesForBook leaves source at 'all', because where a note was
written and which book it is about are different axes.

Mid-fix I wrote `titleOfBook(n.slug)` — a function that does not exist.
Caught by grepping for it before building, which is exactly the
free-identifier crash the guard was written for, authored by the person
who wrote the guard.

19. THE READER STOPS THROWING AWAY WHAT IT FOUND
----------------------------------------------------------------

`chapters` and `chapter_scans` were in the schema from the start, with
views and named queries on top, and NOTHING IN THE APP EVER WROTE TO
EITHER. The only writer was tools/load-library.mjs -- the MinIO loader,
which needs Docker, a manual run and this one machine. Meanwhile
findChapters() ran on every book you opened and the answer was discarded
on close.

The split between the three new writes is the point:
clearDetectedChapters NEVER touches source='hand', and
addDetectedChapter is ON CONFLICT DO NOTHING for the same reason.
recordChapterScan writes a row EVEN WHEN NOTHING WAS FOUND -- that row
is the only thing separating "this book has no chapters" from "nobody
has opened it".

TWO REAL FINDINGS, both from the container refusing:

  a. CREATE OR REPLACE VIEW cannot change a view's shape. A migration
     that reshapes a view MUST DROP IT FIRST.
  b. And dropping in the migration is not enough. applySchema() runs
     schema.sql FIRST and then every migration, on EVERY open -- so
     schema.sql kept recreating the old five-column view and then
     failing to replace the new one, BEFORE the migration that fixes it
     ever ran. THE BASE SCHEMA HAS TO BE THE CURRENT TRUTH.

Caught by status().schemaError, which exists because a database that
answers while behind on its schema is the failure most easily mistaken
for health. Measured 31/31 on the container, then 31/31 again --
genuinely idempotent, not idempotent-looking.

Coverage on the steward's own library: 296 scanned, 194 divided. So 102
real books have no chapters the finder could see -- a number that was
unobtainable that morning.

THE STUDY TABLE'S TRAY. The table worked on exactly one book -- whichever
you had pocketed -- so a second book beside it was impossible. The tray
IS the backpack, filtered by canAccept(), with no third state and no
separate "put down" step, because that is the point of one carry verb.
Notes you carried sit beside the part they belong to.

I BUILT A SURFACE THAT RENDERED SOMETHING NOTHING COULD PRODUCE: the
tray showed carried notes and there was NO WAY TO CARRY A NOTE. The
exact dead-feature shape this project keeps finding, authored the same
hour by the person finding them.

THREE BUGS, ALL ONE THING NAMED TWO WAYS: toolTitle asked deskBook()
while the table asked tableBook(); tableBook() then returned TWO SHAPES
so the heading read "Working through undefined"; and the tray item's
field was called `doc` when it held the WRAPPER, so chips said
"personal-first-book" beside a heading saying "The First Book". None
found by reading. All three from the screenshot or the suite.

THE TERMINAL. `notes`, `notes <word>`, `carry <number>`, `carry`. The
Computer was already an index over everything on this machine and notes
were the one thing it could not list. state.termLast had to grow a KIND
-- it held bare slugs and a numbered row can now be a note.

Two findings from FOLLOWING THE LOOP TO THE OTHER ROOM rather than
stopping when the command said it worked: carrying a note but not its
book landed on "nothing on the table yet" (true, useless -- the book is
named in the note you are holding), and the message fixing that read
"carrying a note about -- bring the book too", with the title missing
from the middle of its own sentence.


21. MY OWN MISTAKES, WHICH ARE THE POINT OF KEEPING THIS
----------------------------------------------------------------

A log of successes teaches nothing. Today's:

  * A TEST BLOCK THAT NEVER RAN. smoke.mjs prints its verdict and exits;
    the whole carrying block was appended AFTER that, so its failures
    went into a list nobody reads. It reported "all checks clean" TWICE.
    Only found by deliberately breaking PLACES and watching the suite
    pass anyway. Two guards that day were born dead; this one was born
    INVISIBLE, which is worse -- a dead guard fails to catch a bug, an
    invisible one also certifies there is none. There is a guard for it
    now.

  * `git checkout <path>` TO UNDO A DELIBERATE BREAK ATE UNCOMMITTED
    WORK. TWICE. Both times the suite caught it. Copy-and-restore, never
    checkout.

  * An assertion that read `open` inside a page context -- which is
    window.open, a function, therefore always truthy. It verified
    nothing at all until it was named.

  * A regex with a LITERAL BACKSPACE BYTE in it (python's \b in a
    heredoc), so an assertion failed while the pages it looked for were
    on screen. The Read tool renders that byte away, so the line looked
    correct. Three detours today came from building test strings through
    python heredocs.

  * Test fixtures that broke rule 1 twice: a migration test using only
    SEED slugs (one of two resolution paths), and a one-page book whose
    unbroken text made paginate() return a single page -- so four
    "hand marks never reach the reader" failures were a guard correctly
    rejecting marks past the end.

  * An assertion checking for the WORD "lost" that failed the correct
    wording, "nothing is lost".

SEVEN TIMES the check was the broken thing, and FOUR real bugs came from
reading the .png after the assertions passed. That is the strongest
signal of the whole session: my assertions test what I expect the code
to do; the screenshot tests what is on the screen.
