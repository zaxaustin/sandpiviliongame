other notes and build plan

The Library is real now. Four shelf blocks map to four lineages — Theravada (NW), Mahayana (NE), Daoism (SW), Practice (SE). Face a shelf, press E, and you get a browsable shelf of actual documents, each opening into a full reading view with sections. Fourteen seeded texts, every one carrying license, source URL, and attribution as first-class fields — including a couple of easter eggs: a steward's note on the Dzogchen/Tao Te Ching distinction, and the Crucible Trial #1 logbook. Marking a text read updates the 📖 counter.
The Study exists — behind a new east door in the Library (a brass arrow sign points the way). Inside are two stations. The Writing Desk is a Hearth-lite day planner: one intention (the flame), your seven rhythm blocks that tap-cycle through waiting → tended → rested, and an evening ember line. The Course Board is where you pin personal paths: title, why, and steps (one per line, with an optional | practice after each). Steps check off, progress bars fill, and a completed course tells you the truth: the walking was the credential. Moss even comments on it if you talk to her.
The architecture is Phase-3-ready. Everything flows through one Store adapter — today it feature-detects localStorage (so in this preview it runs in-memory for the session, but the moment you put this file on Vercel or open it locally in a browser, your days, courses, reading, fish, and even your position survive reloads; the title screen tells you which mode you're in). Swapping in Supabase later means replacing exactly four functions — load, save, listDocs, getDoc — and nothing else. The comment headers in the file mark exactly where to cut it into the Vite modules from the plan.
When you pick this back up, the natural next moves are: drop it into your Vite public/ folder and deploy to see persistence working for real, or start Phase 3 by running that library_documents SQL and I'll help you write the SuttaCentral seeding script.

    src/game/ui/overlays.js  — dialog, shelf, reader, planner, course board
  Root index.html is now just markup + `<script type="module" src="/src/game/main.js">`. Added package.json (Vite as the only dependency) and src/game/style.css holding what used to be the inline <style> block.

What was wrong (found during the split, fixed):
- The Course Board's card list called `onclick="openCourse(id)"` to open a course's detail view — but `openCourse` was never defined anywhere in the original file. Clicking a pinned course from the list silently did nothing (a real dead button, present since this feature was written). Added the missing function.
- Bigger structural issue: the old single `<script>` tag let every top-level `function` auto-attach to `window`, which is how all the inline `onclick="..."` HTML strings (closeUI, openReader, markRead, cycleBlock, createCourse, etc.) resolved. ES modules don't do that — module-scoped functions are invisible to inline HTML handlers. Every module that builds `onclick="..."` markup now explicitly does `Object.assign(window, {...})` for the handlers it needs (see the bottom of ui/overlays.js). If you add a new overlay button with an inline onclick later, remember to export it there too, or switch that overlay to addEventListener-based wiring instead.

What's verified:
- `npm install && npm run dev`, then drove it headlessly with Playwright: title screen, movement, buildings/signs, NPC rendering and wander, and the HUD all work with zero console errors across two separate passes. This also proves out the circular-import chain between entities.js / ui/overlays.js / main.js (each needs functions from the others) — it's safe here because every cross-module reference used before a module finishes loading is a `function` declaration (hoisted), never a `const`.
- Not separately screenshotted: the shelf → reader flow, the writing desk, and the course board's create/toggle/remove path. They go through the same window-exposure fix above, so they should work, but you (a human clicking through it) should give them a real pass before calling this done.

architecture overview — how the pieces actually fit together

  data/seed.js  →  data/store.js  →  scenes.js  →  entities.js  →  ui/overlays.js  →  render.js  →  main.js
  (content)        (persistence)     (world data)  (state+logic)   (DOM panels)       (canvas)      (loop+input, wires it all up)

- Store is the one seam meant to move (localStorage today, Supabase in Phase 3). Everything else
  reads/writes through it; nothing else should ever touch localStorage directly.
- scenes.js is pure data — tile grids plus arrays of npcs/signs/warps/stations. Adding a room means
  adding a build*() function and registering it in `scenes`, nothing more.
- entities.js owns the one mutable `state` object (player position, current dialog/fishing/ui mode)
  and the one `data` object (everything that gets saved). It also does world lookups (tileAt, npcAt,
  blocked, etc.) — anything that answers "what's at this tile."
- ui/overlays.js is the only place that touches the DOM overlay panels (shelf, reader, planner,
  course board) and builds innerHTML with inline onclick strings.
- render.js owns the <canvas> outright and draws every frame; it never mutates state, only reads it.
- main.js is the only place with the requestAnimationFrame loop, keyboard/touch input, and audio.

Known rough edges, worth revisiting before this grows much further:
1. Inline onclick + manual `Object.assign(window, {...})` (see today's update above) works but is a
   footgun — a real class of "silent dead button" bug. Migrating ui/overlays.js to one delegated
   click listener per panel (reading a `data-action` attribute instead of inline onclick) would remove
   this failure mode entirely instead of relying on remembering to update the window-export list.
2. The circular imports between entities.js / ui/overlays.js / main.js work today only because every
   cross-module reference used during load is a `function` declaration (hoisted), never a `const`.
   That's an easy rule to violate by accident later (see the memory note on this). If the café or agent
   work (parts 4-5) adds more cross-module wiring, consider breaking the cycle properly instead of
   adding a fourth circular edge — e.g. pass a small explicit context object into functions instead of
   importing shared mutable state everywhere.
3. `state` currently mixes UI-mode flags (dialog/fishing/ui/courseView) with world/player transform
   in one object. Fine at this size; if the café or workshop rooms add more overlay modes, splitting
   "UI state" from "world state" would keep it readable.
4. `persist()` re-serializes the entire save blob on every micro-action (one block cycle, one step
   toggle). Harmless at localStorage scale; once Phase 3 swaps in network calls, this needs debouncing
   or diffing so every checkbox click isn't a round trip.
5. No save-data versioning. If the planner or course schema ever changes shape, existing localStorage
   saves will silently misbehave rather than migrate. Worth adding a `saveVersion` field and a tiny
   migration function before this has real users depending on their data.
6. Zero automated tests. Reasonable for a solo hobby project, but the openCourse dead-button bug is
   exactly the kind of thing a five-line content-integrity check would have caught (see below).


debugging plan — for later, when something breaks or before picking this back up

Manual smoke-test checklist (run through this after any nontrivial change, since there's no test suite):
  1. Clear localStorage, load the app fresh → title screen → Enter the Grounds.
  2. Walk to each warp (Keep, Library, locked Workshop, the dock) and confirm the right thing happens.
  3. Talk to every NPC (Ember, Moss, Cobalt, Sagara, the Keeper, Quill) — dialog advances and closes.
  4. Open all four library shelves, read at least one doc per tradition, mark one as read, close and
     reopen the shelf to confirm the "read ✓" badge persisted.
  5. Writing Desk: set an intention, cycle all seven blocks through all three states, write an ember
     line, save, close, reopen — confirm everything came back.
  6. Course Board: pin a course with 2+ steps (including one `title | practice` line), confirm it opens
     from the list (this is the button that was silently dead before today), toggle steps, confirm the
     progress bar updates, take it down.
  7. Fish at the pond long enough to see both a catch and a miss; confirm the counter only increments
     on a catch.
  8. Hard-reload the page. Player position, fish count, read docs, today's planner entry, and courses
     should all still be there — this is Store's whole contract.
  9. Devtools console should show zero errors at every step above.

Fault isolation, if a step above fails — check in this order, since it maps to the module boundaries:
  - Blank page, nothing renders at all → console almost certainly has an import/export error (typo'd
    name, wrong path) — check this first after any refactor before looking anywhere else.
  - A specific button or overlay does nothing when clicked → the "forgot to expose it on window" bug
    class; check the `Object.assign(window, {...})` block at the bottom of ui/overlays.js for the name.
  - Movement or animation looks wrong (stutter, wrong speed, teleporting) → entities.js (MOVE_TIME,
    the position-lerp math in main.js's update()), not render.js.
  - A tile, building, or sprite draws wrong or not at all → render.js's drawTile/drawBuilding/drawPerson
    switch statements; confirm the tile character or `type` string actually matches a case — an
    unmatched case fails silently by design, so a typo'd tile letter in scenes.js just draws nothing.
  - Nothing persists across reload → check the text under the title screen's Enter button ("Saving to
    this device" vs "Preview mode"); if stuck in preview mode outside of an iframe, the browser is
    probably blocking localStorage (privacy mode, embedded iframe, etc).
  - A new feature throws "Cannot access 'X' before initialization" at load time → a `const` export got
    used too early across the entities/ui/main circular boundary; see rough edge #2 above.

First automated check worth adding later (still just a plan, not doing it now): a small Node script —
no browser needed — that imports scenes.js and data/seed.js directly and asserts: every warp's `to`
points at a real scene key; every station `kind` has a matching case in main.js's onAction(); every
SEED_LIBRARY slug is unique; every tradition value is one of TRADITIONS. That's exactly the shape of
bug (a config/content typo with no runtime error until a human clicks the wrong thing) most likely to
recur as the Library and Workshop grow, and it's cheap to catch without a full test framework.
