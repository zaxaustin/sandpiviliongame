2. THREE STATES ON A NOTE (data/note-reach.js, new)
----------------------------------------------------------------

  "we should be able to toggle are notes between private and publid
   and we should also add something like ai can read and private is
   truly private."

  SEALED    not reachable. Not by a search, not when you ask, not
            by carrying it in. The ONE state an ask cannot cross.
  ASKABLE   a resident may search it, but only when you press.
            THE DEFAULT.
  PUBLISHED behaves like a book, because you decided that.

lookup.js moved the line from WHO to WHY on 2026-08-07 (asked: yes,
unasked: no). This puts a per-note boundary OUTSIDE that one, so a
visitor can say "not this one, ever" about a single note without
turning the feature off.

ABSENT MEANS ASKABLE, and that is what made it shippable: it is
exactly the rule that already held, so nothing already written
changed reach. Hundreds of existing notes, no migration, no
backfill. The store only ever holds a deliberate departure from the
default -- and setting a note BACK to askable deletes the entry, so
there is one representation of the default rather than two that can
disagree.

A PRESENT BUT UNRECOGNISED VALUE FAILS CLOSED (treated as sealed).
Absence is a statement we make; a strange string is one we cannot
read, and the safe reading of "I cannot tell what this permission
is" is to withhold.

THIS IS NOT visibility.js AND MUST NOT MERGE WITH IT. Two axes:

  visibility.js  CAN THIS LEAVE THE MACHINE?  private/shared/commons
  note-reach.js  MAY A LOCAL MODEL SEE IT?    sealed/askable/published

A note can be private in every sense that matters -- never leaves
this computer, no server has heard of it -- and still be one you are
glad to hand your own resident. If these were one field, sealing a
note would look like unpublishing it. npm test asserts the two
vocabularies do not collide.


3. THE BACKPACK IS GROUNDING, AND IT IS BOUNDED IN TOKENS
----------------------------------------------------------------

carriedBlock() in ui/residents.js is groundingFor()'s first caller.
Given to Quill and the Monk this session; the rest is a named pass.

THE REAL BOUND IS TOKENS, NOT ITEMS. Twenty is a bound on ATTENTION
and the right one for a person. It is not a bound on a context
window: twenty notes is nothing and twenty books is a catastrophe.
The uncapped-prompt bug has now been fixed FOUR times in four
costumes (the Monk's 294 books, the Investigator's seeded
investigations, the Science shelf's summaries, and this) and every
instance was a list capped by COUNT or not at all.

  carrying.js  fitToBudget(items, sizeOf, budget)  - pure, unit-agnostic
  residents.js CARRY_BUDGET = 2000 tokens, CARRY_EXCERPT = 400 chars

Measured with the SAME estimateTokens() the request itself uses. A
second way of measuring drifts from the real one and then lies about
it -- the store.js scar in miniature.

A CARD, NOT A CORPUS. A book contributes its title and shelf; a note
contributes an excerpt. Pulling real passages out of a carried book
is retrieval.js and is deliberately NOT in here, because that is
exactly how a grounding block quietly becomes a corpus again.

fitToBudget ALWAYS KEEPS THE FIRST ITEM, however fat, and reports
`over`. A grounding block that came back EMPTY because the single
carried book had a long title is the silent failure the file exists
to prevent.

SEALED NOTES ARE ABSENT FROM THE PROMPT AND THE MODEL IS NOT TOLD
THEY EXIST. The VISITOR is told, in the bag. Naming an unreadable
note in a prompt only invites a resident to ask after it.

5. ASK A RESIDENT TO SEARCH YOUR NOTES
----------------------------------------------------------------

groundingPlan(q, carrying, {searchMyNotes:true}) finally has a
caller. A SECOND SEND BUTTON beside Ask -- one press, one question,
one search. Deliberately not a toggle: a switch that stays on is a
standing permission wearing a different word.

state.dialog.askNotes is set immediately before the prompt is built
and cleared in a FINALLY, so a message that timed out or threw still
clears the ask. Deleting that finally is the first sabotage case.

The search: syncNotes first (the index is only as fresh as the last
sync), then dbQuery('searchNotes'), then resolve every save_key back
through gatherNotes() -- the save owns the note, the index only
points at it, and a row that will not resolve is dropped rather than
shown, because there is nothing to open or carry.

WHAT IT FINDS LANDS IN THE BACKPACK -- top 3 in hand, the rest
offered with a button each, all of them grounding THAT message. The
steward asked for "dropped straight in"; the top-3 cap is my call on
top of that, and the reason is §3: the bag is the context now, so one
search taking a quarter of it re-creates the bug the bag prevents.
On a full bag they go to the "pick up later" shelf, because
carrying.js already says a full bag is a redirection and not a wall.

THE SEAL IS HONOURED TWICE -- filtered where the block is built, and
re-checked by privacyLeaks() at runtime over everything about to
enter the prompt. Belt and braces on purpose: a guard that is the
ONLY thing between a sealed note and a model is one edit away from
being what failed.

LOCKED WITHOUT A DATABASE, per the steward: "we can say locked for
now... lets get the app done first then we can move on and see what
a website will need". Never a quieter search wearing the same label.


6. TWO OF MY OWN GUARDS WERE BORN DEAD
----------------------------------------------------------------

Thirteen sabotage cases; all thirteen caught NOW. Two were not:

  ONE. The check grepped the WHOLE FILE for `groundingFor(`.
  Deleting the call from carriedLines() left the name in the import
  line and in three comments, so it passed while the backpack was
  not being read at all. That is verbatim the window-export check "a
  comment could satisfy" from CLAUDE.md rule 3.

  TWO. The fix stripped string literals as well as comments, and
  could not parse a REGEX LITERAL. `.replace(/"/g,"'")` in the
  Monk's own prompt reads as a string opening at `/"`; the scanner
  desynchronised, silently swallowed two hundred and fifty lines
  INCLUDING the Monk's `+carriedBlock()`, and reported a real
  composition as missing.

Final form: comments out, strings LEFT IN, look inside the FUNCTION
BODY, and a set of ANCHOR assertions that fail loudly if the
stripper ate real code. A guard that parses has to be held to the
same standard as the thing it guards -- the same lesson as the
prompt-budget guard that read apostrophes in comments as quotes.

That is the fourth and fifth inert guard this repo has produced.
The rate is not falling. Breaking them on purpose is the only thing
that has ever caught one.

ALSO CAUGHT, by an existing guard doing its job: overlays.js called
mayReachNote() without importing it. A bare ReferenceError at
runtime that node --check, the build and every other check would
have passed. That guard was written after the Learning Tree cut
crashed twice on exactly this; it has now paid for itself.

7b. THEN WE RAN IT UNDER ELECTRON, AND IT WAS BROKEN
----------------------------------------------------------------

The section below was written saying the notes search had never
executed end to end and that running it was the highest-value hour on
the board. It was, and it found THREE REAL BUGS in the first run.
Every one of them was invisible to npm test, node --check, the build,
and the browser suite -- the browser LOCKS the button, so the browser
could never have reached this code at all.

  BUG 1 -- A SHADOWED PARAMETER IN THE TEMPORAL DEAD ZONE.
  I named the new option bag `sendChatMessage(q, opts)`. The body
  already declared `const opts = chatOptsFor(d.agent)` INSIDE the try
  block. A block-scoped const shadows the parameter for the WHOLE
  block, so my line reading `opts` at the top of the try threw
  "Cannot access 'opts' before initialization" every single time.

  The feature therefore did nothing at all, and the catch reported it
  to the visitor as "Quill's connection flickers -- the local AI
  didn't answer." Renamed to `sendOpts`.

  BUG 2 -- THE QUESTION IS NOT THE QUERY.
  searchNotes uses websearch_to_tsquery, which ANDs every word. I was
  handing it the visitor's whole sentence. Measured, in the probe:

    "walking"                          -> 2 rows
    "what did I write about walking?"  -> 0 rows

  So the feature would have returned NOTHING for very nearly every
  question a person actually types, while looking like it worked.
  libraryLookupBlock has always used lookupTerms() for exactly this;
  the notes path now uses the same one road, joined with OR. The
  receipt shows the extracted terms ("write, walking"), not the raw
  OR-query -- what was searched is the visitor's business.

  BUG 3 -- THE CONSOLE CAPTURE IN THREE SUITES WAS DEAD.
  `on('console-message', (...a) => { const m = a[1]; ... })`. a[1] is
  the LEVEL, a NUMBER, so `typeof m === 'string'` threw every line
  away and "no console errors" passed no matter what the page logged.
  That is how BUG 1 stayed invisible for three runs.

  Dead in note-search.cjs, records.cjs and chapters-panel.cjs.

  AND A CORRECTION I HAD TO MAKE TO MYSELF. I first wrote that
  packaged-boot.cjs -- THE RELEASE GATE -- was dead too, on the theory
  that Electron 43 emits only an event object. Then I broke its
  capture on purpose and the self-test still passed, which meant the
  theory was wrong, so I measured the signature instead of believing
  it:

    argc = 5
    a[0]  event object: .message (string), .level ('error'/'warning')
    a[1]  level as a NUMBER (3 error, 2 warning)
    a[2]  the message string
    a[3]  line   a[4]  sourceId

  BOTH forms arrive together. packaged-boot read a[2] and was correct
  all along; this gate has been honest since it was written. Getting
  that wrong in the log would have been worse than the original bug --
  a false claim about the release gate, in the file the next person
  trusts. Measured, corrected in three places, and the lesson is the
  house's own: a theory about why something is broken is not evidence
  that it is.

  All four now tolerate either shape, and TWO of them prove their own
  capture: note-search asserts it saw the expected "[chat] … turn
  failed" lines, and packaged-boot deliberately emits a console error
  of its own and fails unless it catches it. Verified by breaking the
  reader on purpose.

AND A FOURTH, IN MY OWN NEW TEST. The check for "the ask does not
linger past one message" reopened the chat with talkTo() before
sending the second message -- which builds a fresh state.dialog with
askNotes:false. Deleting the `finally` entirely still passed. Caught
by sabotage; the second message now stays in the SAME conversation,
which is where a lingering permission would actually bite.

That is the sixth inert guard of the session and the third I wrote
myself. The only thing that has ever caught one is breaking it.

ALSO CHANGED, and it is a small honesty fix with a large blast
radius: sendChatMessage's catch now console.errors the real exception
before showing the kind sentence. It wraps the whole turn, prompt
assembly included, so every bug in OUR code has always been reported
to the visitor as the model failing to answer -- sending them to go
and check Ollama for something we did.

ELECTRON SABOTAGE, 4 of 4 caught: the finally, the seal under an
explicit ask, lookupTerms, and the catch landing in the backpack.

cannot forget. What a role declares instead is a LENS: one line in
roles.js saying what it DOES with what it found, appended after the

with it.

  quill 1527   monk 2949   steward 1331   investigator 1950
  tutor 1480   computer 1255   sebastian 1702      (~tokens)

GUARDS, 5 of 5 broken on purpose and caught: a resident losing the

WHAT THIS BUYS THE NEXT AGENT. Adding an assistant is now an entry in
