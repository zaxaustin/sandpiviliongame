THE CORRECTION THAT STARTED THE DAY
-----------------------------------

The steward, in one sentence:

    "Make me a plan without this beta testing nonsense to figure out
     what we can do you haven't finished the build so I can't test
     anything make sure everything is done before we do that"

This was right, and it is worth being precise about how the mistake
was shaped, because it is not the obvious one.

Nothing was un-built. Everything from the previous week — the pace
charter, note authorship, the AI diagnosis table, the whole five-stage
tutorial, the portable course format — was written, guarded and green.
MAINTAINING.md said so accurately. docs/BETA-READINESS.md said so
accurately.

What both of them ALSO said, at the top of the release gate, was:

    1. A human who is not the steward walks Stage 1 cold.
       Not negotiable, and not substitutable by a green suite.

...while the newest installer was 0.1.0-beta.5, built 2026-08-07, 36
source files behind. Every single thing a tester would have been asked
to walk was absent from the only artifact they could have walked it in.

So the gate was not a gate. It was a shelf. And it had been written
down as a gate in two documents, by me, with the build listed as step
four underneath the human steps that depended on it.

THE RULE THIS COST: never let a gate depend on something only a person
can do while the thing they would do it to does not exist. Build the
artifact first; the human step is then the only step. The gate in
BETA-READINESS.md is now reordered so the machine's half is step one,
struck through, done.

The steward added one hard constraint to the plan:

    "only <=9B models, only one at a time, barely enough room to run
     the game — treat that as a hard limit for this beta"

and two explicit exclusions: no welcome packet, no course steps 2-4.
Both held.


STEP 1 — VERIFY WHAT IS CLAIMED, WITH EVIDENCE
-----------------------------------------------

The plan's first step was deliberately not "build". It was "prove the
things you say are done, are done". Four findings, and two of them
matter more than the build itself.

1a · ai-diagnosis.mjs against the freshly built dist/ — 14/14. All four
     failure states produce four different sentences on screen. The one
     the steward actually hit reads:

       ○ No AI is answering — switch one on
         Nothing is switched on to try, so nothing was contacted at
         all. Enable a connection below.

1b · The full sweep. npm test green. 33 browser suites green. 9
     Electron suites green — docker-home ran 31 real checks rather than
     skipping, so the container home was genuinely covered.

     TWO WERE RED FIRST, AND BOTH WERE STALE TESTS, NOT APP BUGS.

     test/live/teacher.mjs crashed on `packet.kind` of undefined.
     publishFrom() stopped publishing on one press when the "why is
     this worth passing on?" screen landed on 2026-08-09;
     confirmPublish() is what writes the packet now. The suite still
     held the old contract.

     That is my miss, and the lesson is not "I forgot a test". It is
     that every regression list I ran after that change OMITTED this
     suite — so the sweep could not notice it. A sweep that does not
     name the suite cannot fail on the suite. This is rule 4 wearing a
     different coat: a hand-listed set of suites drifts from the
     directory that holds them.

     test/live/storage-room.mjs demanded the word "hundreds" for the
     desktop tier. data/book-storage.js says in its own header why that
     word went: one hundred is not hundreds. It now derives
     DEFAULT_LOCAL_BOOK_CAP, so correcting the cap corrects the suite.

     It also demanded "no practical limit" for Docker on a page being
     rendered to a BROWSER TAB, which cannot reach Docker at all. The
     room is right to withhold a ceiling it cannot offer — the check
     three lines above already asserts the Docker command is withheld
     from a tab. Promising the ceiling while withholding the means
     would have been the same dishonesty in reverse. Verified by probe
     before touching it: the panel renders "500 books by default".

1c · Six measured numbers had drifted:

       overlays.js       13,671 and 13,591  ->  13,694
       game source       27,427             ->  27,725
       browser suites    32                 ->  33
       assertion sites   809                ->  826
       open plans        60                 ->  61

     The overlays line-count guard has a 150-line tolerance, which is
     exactly the band these were sitting in. A guard with a tolerance
     is a guard that goes quiet inside it.

1d · AND THE HARDWARE FALSIFIED A LINE OF SHIPPED ADVICE.

     The Connections panel's tiered guide read:

       Strong (12GB+ VRAM) — an 8-14B instruct, plus optionally one
       "thinking" model.

     The steward measured a 12B on a 16GB Arc A770: 13.8 of 16.0 GB
     dedicated, 0.4 GB spilled to shared memory, every token thereafter
     waiting on the PCIe bus. A card ABOVE that floor cannot hold the
     middle of that range, let alone two models at once.

     It does not fail. It crawls — which is the harder thing to
     diagnose, and exactly the kind of failure a tester blames
     themselves for.

     Now: 9B is the honest ceiling, one model at a time, with the
     measurement cited in the panel itself. checkMyMachine() was
     checked in the same pass and is clean — it caps at llama3.1:8b.

     This is the pattern worth keeping: the hardware constraint was
     handed over as a limit on what to TEST, and it turned out to be a
     bug report about what we SAY.


STEP 2 — THE BUILD, AND A GAP IN "TEST THE ARTIFACT YOU SHIP"
--------------------------------------------------------------

package.json -> 0.1.0-beta.6. The in-app Build: string is derived by
vite.config.js from package.json, so there was nothing to hand-type.

  npm run build:beta
  npm run electron:build:beta -- --config.directories.output=$TEMP/sp-build

The EPERM gotcha is real and the documented workaround worked first
time. Copied the .exe back into release/.

packaged-boot.cjs: SHIPPABLE, 7/7.

AND THEN THE THING WORTH RECORDING. Rule 8 says TEST THE ARTIFACT YOU
SHIP. packaged-boot.cjs does not do that. It reproduces the packaged
LOAD PATH — same preload, same contextIsolation, same
loadFile(dist/index.html) — using the repo's own electron against the
repo's own dist/ directory. That is the check that caught a title
screen with nothing behind it, and it is still the right fast check.

But dist/ is not the artifact. Between dist/ and the .exe sit:

  - the asar pack
  - the `files` glob in package.json (does tools/migrations/*.sql
    actually make it in?)
  - asarUnpack for PGlite's WASM
  - the icon, and the signing step

None of that was exercised by anything, ever. "Test the artifact you
ship" was three-quarters true and had been for months.

So: test/live/packaged-exe.mjs. It launches the real binary out of
win-unpacked with a throwaway --user-data-dir (it cannot touch the
steward's save) and drives it over CDP. It asserts the app loads out of
app.asar over file://, that the bundle ran, that the desktop bridge is
present, that the database opens AND ITS SCHEMA APPLIED INSIDE THE
PACK, that the Build: line a tester reads back to us is the version in
package.json, and that "Enter the Grounds" enters.

  PASS  it loaded out of app.asar over file://
  PASS  the game's own code is running
  PASS  the desktop bridge is wired up
  PASS  the packaged app reaches a database
  PASS  and its schema applied cleanly inside the pack
        {"up":true,"kind":"docker","schemaError":null,...}
  PASS  the app names itself 0.1.0-beta.6
  PASS  and it knows it is the installed app, not a tab
  PASS  "Enter the Grounds" actually enters
  PASS  no page errors

BROKEN ON PURPOSE (rule 3): bumped package.json to 0.1.0-beta.7 and
re-ran against the beta.6 binary. It failed on exactly the right line
and printed the real one:

  FAIL  the app names itself 0.1.0-beta.7  <- Build:  0.1.0-beta.6

That is the drift it exists to catch, reproduced.

A GOTCHA THAT COST A DETOUR AND IS NOW IN CLAUDE.md RULE 8:
ELECTRON_RUN_AS_NODE was set to 1 in this shell. With it set, the
packaged .exe runs as node, rejects --user-data-dir with

  Sand Pavilion.exe: bad option: --user-data-dir=...

and exits 9. From the outside that is INDISTINGUISHABLE from a packaged
app that crashes on boot — I spent several minutes believing I had cut
a broken installer. The suite now refuses to run when the variable is
set, rather than reporting a fake failure. CLAUDE.md already warned
about this variable for require('electron'); it turns out to break the
.exe far more spectacularly.

Two false starts before that, both mine and both cheap: the check first
looked for window.desktop and window.showOv, when the real names are
window.desktopBridge and window.openWelcome (packaged-boot.cjs already
knew this); and the version is not on the title screen at all — it
lives in the bug-report card, which is the one place a tester reads it
back to us, so that is where the check reads it.

Also: a stray invalid C:\Users\...\Temp\package.json makes node refuse
to resolve ESM imports for any script run out of the temp directory
(ERR_INVALID_PACKAGE_CONFIG). Not ours, but worth knowing — scratch
.mjs files must live inside the project.

Then the installer was rebuilt once more, because verifying the version
guard by editing package.json had made package.json newer than the
.exe, and verify:release counts that (correctly) as "the installer is
older than the source". Restoring a file does not restore its mtime.
Rebuilding is the honest answer; touching the file to defeat a
freshness check is the dishonest one.

  release/Sand Pavilion Setup 0.1.0-beta.6.exe   101 MB
  SHA256 D8C6BF5780F5CD2D5D1E5E41D73502BC4520F525BD1ABD007757AF64E3592325

Both artifact suites re-run green against the rebuild.

PART TWO — THE DOOR FOR A COMPUTER THAT CANNOT RUN A MODEL
================================================================

The steward, after the build was cut:

    "How is the ollama connection for the cloud because I know my
     friend is not gonna be able to run any models on his computer but
     I still wanna get him access to this... make sure there's a
     pathway in the game for that to happen especially for the Mac
     build."

THE ANSWER WAS ALREADY BUILT AND NOBODY COULD FIND IT, which is the
worst version of this and the one rule 5 is about.

Everything in the engine has worked since 2026-08-03. Ollama serves
hosted models through the SAME local endpoint, so no API key is ever
pasted into this app. isCloudModel() marks them on two independent
signals (the name, and the size — a hosted entry is a ~306-byte
manifest where a real model is gigabytes). They are excluded from every
automatic choice, and honoured when the visitor picks one deliberately.
p.usingCloud is set, the connection renames itself "☁ hosted", the chat
header says "leaves this device". A CLOUD_ONLY trouble state exists and
says the right thing. Measured that day: gpt-oss:20b-cloud answered in
0.64s where a local 9B takes many seconds.

And the ONE surface where a person would look — "Check this computer",
written for exactly this friend in July — said:

    "Skip the AI on this machine — and lose nothing that matters.
     4 GB isn't enough... So: don't."

True about LOCAL models. False about the Pavilion, by omission. The
machine most in need of the door was the only one being told to give
up, and the only people who could find the door were the ones who
already knew it was there.

WHAT WAS ADDED. data/machine-advice.js gains CLOUD_MODEL, CLOUD_CAVEAT
and cloudPathway(tier), and recommendModel() now returns `cloud:` on
EVERY tier — never null, so there is no branch that can drop it. Only
`prominence` changes: 'primary' for none/tight/unknown, 'aside' for a
machine that can run its own. Two rules are written into the module
header rather than left to whoever edits the copy next:

  · never offer it without saying plainly that it leaves the device.
    A pathway out of the promise is fine; a QUIET pathway out of it is
    not.
  · never lead with it on a machine that can run local. Local is the
    disposition; this is the door for the people the disposition
    excludes.

Rendered in three places: the machine card (a bordered ☁ block with
both commands and a Copy button each), the tiered guide in Connections
(a "None of the above?" row, so it is visible before pressing
anything), and AI_TROUBLE.NO_MODELS gains one clause.

FIVE GUARDS, ALL BROKEN ON PURPOSE, AND ONE WAS BORN DEAD.

  1. cloud: deleted from the return          -> 9 failures, named
  2. the caveat's warning half deleted       -> PASSED. see below
  3. signin and pull swapped                 -> 1 failure, named
  4. tag changed to gpt-oss:20b (not hosted) -> 1 failure, named
  5. prominence forced to primary everywhere -> 5 failures, named

Guard 2 was born dead in the textbook way. It read

    /leave|does not stay/i.test(caveat)

and the caveat's SECOND half is the reassurance "...your whole save
never leave". So deleting the entire outbound warning still passed: the
word survived inside the sentence that says the opposite. It checked
the word, not the statement — the same shape as every born-dead guard
in CLAUDE.md rule 3. Both halves are asserted separately now, and
re-broken both ways to prove it.

Guard 4 is the one worth keeping deliberately: it asks provider.js's
own isCloudModel() whether the tag the ADVICE recommends is one the
PICKER will treat as hosted. Two files, one fact, checked across the
seam. Without it, renaming the recommended tag would quietly recommend
a model that could then be auto-picked — which is the 2026-08-03 bug
(the Monk's private conversations going to a server) re-introduced from
the advice side rather than the engine side.

Live: ai-diagnosis.mjs gains a fifth section that presses "Check this
computer" and reads the panel — 19/19. One real bug in the test itself:
innerText of a CLOSED <details> is the summary alone, so the tiered
guide check failed on correct code until it set `d.open = true`.

AND I LOOKED AT IT (rule 2). A scratch page with navigator.deviceMemory
forced to 4 renders the primary card, screenshotted to
test/live/_hosted-primary.png. It reads correctly: the "don't run one
locally" verdict, then the ☁ block, then the two commands, then the
caveat in amber, then "press Detect and choose it — hosted models are
never picked for you."

The verdict line was also corrected. "Skip the AI on this machine" is
now "Don't run a model on this machine", and the paragraph ends "If you
want the residents anyway, there is a hosted way below" — because a

THE MAC BUILD
--------------

    "let's make sure that there is a Mac install as well I wanna make
     sure my friend can try this on his laptop"

.github/workflows/build-installers.yml has built both platforms since
2026-07-28 and NOBODY HAD EVER PUSHED A TAG TO FIRE IT. package.json
already asks for arm64 AND x64 dmgs, unsigned (identity: null).

So the Mac build needs no code — it needs the tag. What it does need is
honesty about what cannot be verified from here: nothing on this
Windows machine can build or test a .dmg, so the CI log is the only
evidence until a Mac opens one. Recorded in SHIPPING-THE-BETA.md, along
with the two things that will actually bite: an arm64 build will not
open on an Intel Mac (ask which he has), and Gatekeeper says "Sand
Pavilion is damaged and can't be opened" about every unsigned app,
which frightens people far more than SmartScreen.

The release notes now carry all three install paths — .exe, both .dmgs,
and the website for anyone who wants none of it.
